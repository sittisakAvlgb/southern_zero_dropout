# Southern Zero Dropout — UX/UI Redesign Brief

> โจทย์จากเจ้าของโปรเจกต์ · ตุลาคม 2026
> อ่าน [ux-redesign-gap-analysis.md](ux-redesign-gap-analysis.md) ควบคู่ก่อนเริ่มลงมือ

## Project Meaning

Southern Zero Dropout คือระบบสำหรับ **เฝ้าระวัง ป้องกัน และช่วยเหลือนักเรียนก่อนหลุดออกจากระบบการศึกษา** โดยมี **“คุณครู” เป็นผู้ใช้งานหลักของระบบ**

แนวคิดของ Project ไม่ใช่การรอให้นักเรียนหลุดจากระบบแล้วจึงเข้ามาดูข้อมูล แต่ต้องช่วยให้โรงเรียนสามารถ **รู้ก่อน → เข้าใจปัญหา → ช่วยก่อน → ติดตามผล**

เพราะคุณครูคือคนที่อยู่ใกล้นักเรียนมากที่สุด และสามารถสังเกต ติดต่อ พูดคุย และเริ่มต้นการช่วยเหลือได้เร็วที่สุด

ระบบนี้ไม่ควรถูกออกแบบเป็นเพียง Management Dashboard แต่ควรเป็น **Teacher Workspace / AI Assistant สำหรับครู** ที่ช่วยลดภาระในการดูข้อมูลจำนวนมาก และช่วยให้คุณครูรู้ว่า

- วันนี้มีนักเรียนคนไหนต้องดูแล
- นักเรียนคนไหนมีความเสี่ยงเพิ่มขึ้น
- นักเรียนเสี่ยงจากอะไร
- ควรเริ่มช่วยอย่างไร
- เคยมีการช่วยเหลืออะไรไปแล้ว
- ต้องติดตามอะไรต่อ
- ผลการช่วยเหลือดีขึ้นหรือไม่
- เคสไหนสามารถปิดได้

เป้าหมายสำคัญคือ **ป้องกันเด็กก่อนหลุด** · กรณีนักเรียนหลุดออกจากระบบแล้ว ระบบสามารถแสดงข้อมูลและสถานะเพื่อส่งต่อให้หน่วยงานที่เกี่ยวข้องดำเนินการต่อได้ แต่ไม่ควรเป็น Core Experience หลักของ Product

## Product Vision

> “ระบบเฝ้าระวังและช่วยเหลือนักเรียนเชิงรุกสำหรับครู เพื่อให้ครูมองเห็นความเสี่ยงก่อนเด็กหลุด เข้าใจสาเหตุ และได้รับคำแนะนำในการช่วยเหลือที่เหมาะสมกับนักเรียนแต่ละคน”

**Core Concept:** รู้ก่อน → เข้าใจสาเหตุ → AI ช่วยแนะนำ → ลงมือช่วย → ติดตาม → เห็นผล

## Primary User

ออกแบบโดยยึด **คุณครูเป็น Primary User** ลำดับความสำคัญของ Experience คือ

```
ครู → นักเรียน/Case → โรงเรียน → เขตพื้นที่การศึกษา → ผู้บริหาร
```

ไม่ควรเริ่มออกแบบจาก Dashboard ผู้บริหารแล้วค่อยลดรายละเอียดลงมาหาครู ให้เริ่มจากคำถามว่า **“คุณครูต้องทำอะไรกับนักเรียนในแต่ละวัน?”** แล้วนำข้อมูลจากการทำงานของครูขึ้นไปสรุปให้ ผอ. และเขตภายหลัง

## UX/UI Redesign Goal

เป้าหมายหลักไม่ใช่แค่ปรับ Visual ให้สวยหรือทันสมัยขึ้น แต่ต้องทำให้ผู้ใช้ **เข้าใจง่าย → เห็นสิ่งสำคัญ → รู้ว่าต้องทำอะไรต่อ**

ทุกหน้าควรตอบคำถามได้ 3 ข้อ

1. เกิดอะไรขึ้น?
2. อะไรสำคัญที่สุด?
3. ฉันต้องทำอะไรต่อ?

## Main User Flow

```
พบความเสี่ยง → เข้าใจสาเหตุ → AI ช่วยสรุปและแนะนำ → ครูเลือกแนวทางช่วยเหลือ
→ ครูดำเนินการ → ติดตามผล → ดีขึ้น = ปิดเคส / ยังเสี่ยง = แนะนำ Next Action
```

Flow นี้ควรเป็นแกนกลางของ UX ทั้งระบบ

## 1. Redesign Teacher Home

หน้าแรกของครูเป็นหน้าที่ควรให้ความสำคัญสูงสุด ไม่ต้องการ Dashboard ที่เต็มไปด้วยกราฟหรือ Card จำนวนมาก ครูเปิดระบบมาแล้วควรรู้ทันทีว่า **“วันนี้ฉันต้องทำอะไร?”**

ข้อมูลสำคัญที่ควรเห็นก่อน (ตัวอย่าง): 8 คน นักเรียนเสี่ยงสูง · 3 คน ต้องติดตามวันนี้ · 12 คน กำลังอยู่ระหว่างช่วยเหลือ · 5 เคส รอประเมินผล

จากนั้นระบบควรบอก **สิ่งที่ต้องทำวันนี้** เช่น

- นักเรียน 3 คนต้องติดตามวันนี้
- นักเรียน 2 คนมีระดับความเสี่ยงเพิ่มขึ้น
- 4 เคสไม่มีการอัปเดตเกิน 7 วัน

และมี **Primary Action ที่ชัดเจน** เช่น “ดูนักเรียนที่ต้องติดตาม”

## 2. Redesign Student Detail

เปิดมาแล้วต้องเข้าใจสถานการณ์ของนักเรียนได้อย่างรวดเร็ว ต้องตอบให้ได้ว่า

| | |
|---|---|
| **Risk** | นักเรียนอยู่ในระดับความเสี่ยงอะไร |
| **Why** | เสี่ยงเพราะอะไร — ขาดเรียนต่อเนื่อง · ผลการเรียนลดลง · ปัญหาครอบครัว · ปัญหาเศรษฐกิจ · พฤติกรรมเปลี่ยนแปลง |
| **History** | เคยได้รับการช่วยเหลืออะไรไปแล้ว |
| **Next Action** | ครูควรทำอะไรต่อ |

ไม่ควรให้ครูต้องเปิดหลาย Tab หรืออ่านข้อมูลจำนวนมากก่อนที่จะเข้าใจ Case

## 3. Case Flow

ออกแบบสถานะ Case ให้เข้าใจง่ายและเรียงตามงานจริงของครู

```
พบความเสี่ยง → รอดำเนินการ → กำลังช่วยเหลือ → ติดตามผล → ช่วยเหลือสำเร็จ → ปิดเคส
```

ทุก Case ควรเห็นได้ว่า: ใครรับผิดชอบ · Action ล่าสุดคืออะไร · อัปเดตล่าสุดเมื่อไร · ต้องทำอะไรต่อ · นัดติดตามเมื่อไร · สถานะปัจจุบันคืออะไร

## 4. AI Assist

AI ไม่ควรเป็นเพียง Chatbot แยกอยู่มุมหนึ่งของระบบ **AI ควรแทรกอยู่ใน Workflow การทำงานของครู**

- **AI Risk Summary** — สรุปว่านักเรียนคนนี้มีความเสี่ยงอะไร และเกิดจากปัจจัยใด
- **AI Recommended Action** — ตอบคำถามสำคัญที่สุดว่า “แล้วครูควรทำอะไรต่อ?” เช่น ติดต่อผู้ปกครอง · พูดคุยกับนักเรียน · ตรวจสอบสาเหตุการขาดเรียน · ประเมินด้านเศรษฐกิจ · ติดตามผลภายใน 7 วัน
- **AI Assistant** — ถามด้วยภาษาธรรมชาติ เช่น “วันนี้มีนักเรียนคนไหนต้องติดตามบ้าง” · “เด็กคนนี้ควรช่วยอย่างไร” · “มีนักเรียนคนไหนขาดเรียนต่อเนื่อง” · “ช่วยสรุปนักเรียนเสี่ยงในห้องนี้ให้หน่อย” · “มีเคสไหนที่ยังไม่ได้ดำเนินการ”

AI ต้องทำหน้าที่เป็น **ผู้ช่วยครูในการตัดสินใจ** ไม่ใช่ Feature ที่แยกออกจาก Workflow

## 5. Dashboard ผอ. / โรงเรียน

เน้น **KPI ก่อนกราฟ** — นักเรียนทั้งหมด · นักเรียนเสี่ยง · กำลังช่วยเหลือ · ช่วยเหลือสำเร็จ · ยังไม่ได้ดำเนินการ · เคสที่ไม่มีการอัปเดต

จากนั้น Drill Down ไป ระดับชั้น → ห้อง → ครู → นักเรียน

เป้าหมาย: ให้ ผอ. รู้ว่า “ตอนนี้โรงเรียนของฉันมีปัญหาตรงไหน และควรเข้าไปสนับสนุนตรงไหน”

## 6. Dashboard เขตพื้นที่การศึกษา

Hierarchy หลักเป็น **เขตพื้นที่การศึกษา → โรงเรียน → นักเรียน** · ไม่จำเป็นต้องใช้ “จังหวัด” เป็น Navigation Level หลัก จังหวัดเก็บเป็นข้อมูลหรือ Filter ได้

ควรตอบได้ทันทีว่า: มีนักเรียนเสี่ยงกี่คน · กำลังช่วยเหลือกี่คน · ช่วยได้แล้วกี่คน · ยังไม่ได้รับการช่วยเหลือกี่คน · โรงเรียนไหนมีความเสี่ยงสูง · โรงเรียนไหนต้องเข้าไปสนับสนุน · โรงเรียนไหนไม่มีการอัปเดต

เน้นให้ผู้บริหารรู้ **จุดที่ต้องสนใจ** มากกว่าดูกราฟจำนวนมาก

## 7. User Activity / Last Active

เพิ่มข้อมูลเพื่อช่วยให้ ผอ. และเขตเห็นการใช้งานจริง เช่น คุณครูเข้าใช้งานล่าสุด · Case อัปเดตล่าสุด · โรงเรียนอัปเดตข้อมูลล่าสุด · Case ที่ไม่มีการเคลื่อนไหวเกิน 7 วัน · โรงเรียนที่ไม่มีการใช้งานช่วงที่ผ่านมา

⚠️ UX และข้อความต้องระวังไม่ให้ดูเหมือนระบบสำหรับ **“จับผิดครู”** ให้สื่อว่าเป็นข้อมูลสำหรับช่วยให้ผู้บริหารทราบว่าพื้นที่ใดต้องได้รับการสนับสนุน

## 8. Mobile First

Role ครูต้องออกแบบแบบ Mobile First เพราะครูอาจใช้งานในห้องเรียน · ระหว่างพูดคุยกับนักเรียน · ระหว่างเยี่ยมบ้าน · นอกสำนักงาน · ในพื้นที่ที่อินเทอร์เน็ตไม่เสถียร

ตรวจเป็นพิเศษ: **Typography** คมและไม่เล็กเกินไป · **Button** กดง่ายด้วยนิ้ว · **Spacing** เหมาะกับ Mobile · **Information Priority** ไม่เอาข้อมูล Desktop ทั้งหมดมาย่อใส่มือถือ · **Responsive** Table/Card/Chart ออกแบบใหม่ตามพื้นที่หน้าจอ · **Primary Action** อยู่ในตำแหน่งที่มองเห็นและกดง่าย

## 9. UX Information Hierarchy

ใช้ Principle เดียวกันทั้งระบบ: **NUMBER → INSIGHT → ACTION → DETAIL**

```
NUMBER    8 คน มีความเสี่ยงสูง
   ↓
INSIGHT   3 คนมีความเสี่ยงเพิ่มขึ้นในสัปดาห์นี้
          AI Summary: “สาเหตุหลักมาจากการขาดเรียนต่อเนื่อง”
   ↓
ACTION    [ ดูนักเรียน 3 คน ]
   ↓
DETAIL    จึงค่อยเข้าไปดูข้อมูลรายนักเรียน
```

ไม่ควรออกแบบเป็น Chart → Chart → Chart → Table แล้วให้ผู้ใช้ตีความเอง

## 10. UX States

ออกแบบ State ให้ครบ ไม่ใช่เฉพาะหน้าที่มีข้อมูล — Empty · Loading · Skeleton Loading · Error · Success · AI Processing · No Search Result · No Risk Student · No Active Case · Offline/Network Problem สำหรับ Mobile

## 11. Clickable Prototype

ทำ Clickable Prototype เพื่อทดสอบกับ User จริง อย่างน้อย 3 Scenario

**Scenario 1 — พบเด็กเสี่ยงใหม่**
Home → เห็น Alert → เปิด Student → ดู AI Summary → ดู Recommendation → เริ่ม Case → บันทึกการช่วยเหลือ

**Scenario 2 — ติดตาม Case เดิม**
Home → เห็น Case ที่ต้องติดตามวันนี้ → เปิด Case → ดูข้อมูลล่าสุด → บันทึกผล → AI แนะนำ Next Action → นัดติดตามครั้งต่อไป / ปิด Case

**Scenario 3 — ผู้บริหารดูสถานการณ์**
Dashboard → เห็น KPI → พบจุดที่ต้องสนใจ → Drill Down → โรงเรียน → นักเรียน/Case ที่เกี่ยวข้อง

## Design Principle

> **“ครูเข้ามาเพื่อทำงาน ไม่ได้เข้ามาเพื่อดู Dashboard”**

| ให้ความสำคัญกับ | มากกว่า |
|---|---|
| Action | Decoration |
| Insight | Raw Data |
| Recommendation | Report |
| Student Case | Chart |
| Teacher Workflow | Management Dashboard |

## Definition of Done

งานรอบนี้ไม่ควรจบเพียงว่า “UI ดูทันสมัยขึ้นแล้ว” แต่ต้องผ่านเกณฑ์ว่าเมื่อ User เปิดแต่ละหน้าแล้วตอบได้ภายในเวลาอันสั้นว่า

1. เกิดอะไรขึ้น?
2. อะไรสำคัญที่สุดตอนนี้?
3. ฉันต้องทำอะไรต่อ?

**ถ้ายังตอบ 3 คำถามนี้ไม่ได้โดยไม่ต้องมีคนอธิบาย แสดงว่า UX ของหน้านั้นยังไม่เสร็จ**
