## ⚠️ 4 เรื่องที่ต้องตัดสินใจก่อนลงมือ — อย่าเพิ่งเขียนโค้ด

### 1. ข้อ 6 — “ไม่ใช้จังหวัดเป็น Navigation Level หลัก”

**สิ่งที่ brief ขอ มีอยู่แล้ว** — role `esa` (สำนักงานเขตพื้นที่การศึกษา) ทำ **เขต → อำเภอ → โรงเรียน → นักเรียน** อยู่แล้วตรงตามที่ขอ ดู `ROLE_NAV.esa` และ `esaOfDistrict()` ใน `src/data/esa.ts`

ที่อาจทำให้เข้าใจว่ายังไม่มี เพราะบัญชีเดโมที่เปิดมาเจอก่อนคือ **สพฐ.** ไม่ใช่ **สพท.** → ลองล็อกอินด้วยบัญชี สพท. ก่อนตัดสินใจรื้ออะไร

**เตือนสำคัญ:** `provinceKey` / `districtKey` / `esaKey` ไม่ใช่แค่ nav — มันเป็นแกนของ **PDPA scoping** ทั้งระบบ (`inTerritory()`, `useScopedData()`) การเปลี่ยนลำดับชั้นการนำทางทำได้ แต่ **ห้ามแตะ scope logic** ไม่งั้นบัญชีหนึ่งจะเห็นชื่อเด็กนอกเขตตัวเอง ซึ่งไม่ใช่บั๊ก UI แต่เป็นการละเมิด PDPA

### 2. ข้อ 7 — User Activity / Last Active

ตอนนี้ **ยังไม่มี** การเก็บ activity ของผู้ใช้เลย (ไม่มี `lastActive`/`lastLogin` ที่ไหนในโค้ด) จะทำต้องเพิ่มฟิลด์ใหม่

brief เองก็เตือนว่าห้ามให้ดูเหมือน “จับผิดครู” — ขอเพิ่มอีกชั้น: ในพื้นที่ จชต. การเก็บ log รายบุคคลของครูแล้วให้ผู้บริหารเห็น เป็นเรื่องอ่อนไหวกว่าปกติ

**คำถามถึงเจ้าของโปรเจกต์:** เก็บและแสดงผลที่ระดับ **โรงเรียน (aggregate)** แทน **ครูรายคน** ได้ไหม — ได้ข้อมูลที่ผู้บริหารต้องการ (“พื้นที่ไหนต้องสนับสนุน”) โดยไม่สร้างเครื่องมือประเมินรายบุคคล

### 3. ทะเบียนเด็กนอกระบบ (OOSC) ลดความสำคัญได้ แต่ห้ามถอด

brief บอกว่าเด็กที่หลุดแล้ว “ไม่ควรเป็น Core Experience” — **ปรับลำดับใน UI ได้** แต่ `/oosc` เป็น deliverable ตาม **TOR ๔.๓** ถ้าถอดออกหรือซ่อนจนหาไม่เจอ จะตกข้อกำหนดตอนตรวจรับ

### 4. Primary user คือครู แต่ครูเข้าถึงได้แค่ 5 หน้า

```ts
teacher: ['/', '/plan', '/referral', '/intervention', '/student', '/settings']
```

ถ้าจะทำ teacher-first จริง ควรทบทวนว่า `/oosc` ควรอยู่ในมือครูด้วยหรือไม่ — **เป็นการตัดสินใจเชิงสิทธิ์ ไม่ใช่เชิง UI** ต้องถามก่อนแก้ `ROLE_NAV`

> 📌 อีกเรื่องที่ brief ไม่ได้พูดถึงแต่ต้องรู้: role **`exec` (ผู้บริหารจังหวัด) และ `agency` (หน่วยงานส่งต่อ) ถูกซ่อนอยู่** ใน build นี้ (`HIDDEN_ROLES` ใน `src/auth/roles.ts`) โค้ดยังอยู่ครบ แค่ไม่ถูกเสนอให้ล็อกอิน

## 🔨 งานใหม่จริง — เรียงตามความยาก

### ① AI แทรกใน workflow (ข้อ 4) — ต้องแก้สถาปัตยกรรมก่อน

ทุกวันนี้ AI **ทำได้แค่ตอบกับชี้ทาง** เพราะ `ChatAction` มีแค่

```ts
export interface ChatAction { label: string; to: string }   // src/lib/ai.ts:138
```

คือปุ่มที่พาไปอีกหน้า — มัน *ทำ* อะไรให้ครูไม่ได้เลย

**“AI Recommended Action” ตามข้อ 4 ต้องการ action ที่เขียนข้อมูลได้** (เช่น “บันทึกว่าติดต่อผู้ปกครองแล้ว” แล้วสถานะเปลี่ยนจริง) → ต้องเพิ่ม action ชนิดใหม่ก่อน แล้วค่อยทำ UI

**กฎที่ห้ามข้าม:** action ที่เขียนข้อมูลทุกตัวต้องผ่าน `canWorkCases()` — บัญชี สพฐ./ศอ.บต. เป็น read-only ทั้งระบบ และ **AI ต้องไม่กลายเป็นทางลัดข้ามสิทธิ์**

### ② Mobile-first re-pass (ข้อ 8) — งานใหญ่กว่าที่เห็น

มี bottom nav แล้วก็จริง แต่หน้าเนื้อหายังเป็น desktop-first

ข้อมูลผู้ใช้ที่ต้องยึด: **ครูบางท่านอายุมาก** ดังนั้นทิศทางคือ **เพิ่ม**ขนาดตัวอักษร ไม่ใช่ลด — ตอนนี้ `Student360.tsx` ใช้ label `text-[10px]` และค่า `13px` ซึ่งเล็กเกินไปสำหรับสายตายาวอยู่แล้ว · ห้ามใช้ affordance ที่ต้อง hover (มือถือแตะไม่ได้) · ห้ามแลก contrast กับความสวย

### ③ User Activity (ข้อ 7) — ต้องเพิ่ม data model

ไม่มีฟิลด์ใดรองรับเลย ต้องเพิ่มใน `User` และ/หรือ `CaseRecord` → **รอคำตอบข้อ 2 ด้านบนก่อน** ว่าจะเก็บระดับไหน

### ④ UX States ให้ครบ (ข้อ 10)

เครื่องมือมีแล้ว งานคือไล่ใช้ให้ครบทุกหน้า โดยเฉพาะ **Offline** ซึ่งยังไม่มีเลย และสำคัญกับโจทย์ “ครูใช้ตอนเยี่ยมบ้าน พื้นที่เน็ตไม่เสถียร”

## แนะนำลำดับการลงมือ

1. **ล็อกอินครบทุก role ก่อนเขียนโค้ดบรรทัดแรก** (สพฐ. · สพท. · ผอ. · ครู) — ครึ่งหนึ่งของ brief อาจมีอยู่แล้วแต่อยู่ใน role ที่ยังไม่ได้เปิดดู
2. **ถามเจ้าของโปรเจกต์ 4 ข้อด้านบน** แล้วบันทึกคำตอบกลับมาในไฟล์นี้
3. เริ่มจากงานที่ไม่ต้องรอคำตอบ: **ข้อ 2 (ย้าย “Why” มาอยู่กับคะแนนเสี่ยง)** และ **ข้อ 9 (NUMBER → INSIGHT → ACTION)** บนหน้าครู — สองอันนี้ใช้ข้อมูลที่มีอยู่แล้วทั้งหมด ไม่ต้องแตะ data layer หรือ auth
4. งาน AI (ข้อ 4) ไว้ทีหลัง เพราะต้องแก้สถาปัตยกรรมและต้องรีวิวเรื่องสิทธิ์
